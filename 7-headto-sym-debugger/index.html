7 从源码到可调试进程

从源码到可调试进程

从一条断点说起

第6章结束时，我们的调试器已经能启动进程、跟踪线程、下断点、单步、读写内存和寄存器。但它只认识地址，所以我们只能这样下断点：

(godbg) break *0x4b85af
Breakpoint 1 at 0x4b85af

而我们真正想要的是：

(godbg) break main.go:19
Breakpoint 1 at 0x4b85af: file main.go, line 19.
(godbg) continue
...
(godbg) print pid
$1 = 12345
(godbg) bt
#0 main.main() at main.go:19
#1 runtime.main() at /usr/local/go/src/runtime/proc.go:283

从 break *0x4b85af 到 break main.go:19，从 print *(int64*)($rsp+8) 到 print pid，中间隔着一整条“符号 ↔ 符号地址（链接地址、运行时地址）、源码 ↔ 机器（源码位置、机器指令地址）”的转换链。这条链上的每一环，都对应本章或第8章的一节：

调试器要回答的问题 依赖的数据 本书哪里讲
源码 main.go:19 对应哪条指令？ DWARF 行号表 8.5.2
函数 main.main 的地址范围是多少？ 符号表、DWARF DW_TAG_subprogram 7.3、8.4.3
变量 pid 在寄存器里还是栈上？ DIE + 位置表达式 8.4.1、8.4.2
当前 PC 属于哪个函数、哪一层调用？ CFI（.debug_frame） 8.5.3
文件里的地址和进程里的地址怎么换算？ ELF 段、PIE、装载偏置 7.2、7.5、7.6
这些调试信息是谁、在什么时候写进二进制的？ 编译器、链接器 7.1、8.6
怎么在 Go 里把它们读出来？ debug/elf、debug/gosym、debug/dwarf、自研 pkg/dwarf（参考 delve） 7.7、8.7–8.9

这张表就是本章的“地图”。它有两个轴：符号 ↔ 符号地址（名字在哪儿）和 源码 ↔ 机器（代码在哪儿）；前者的地址又分链接地址和运行时地址，后者由行号表和 CFI 连起来。符号级调试器不是一堆命令的集合，而是这条转换链的实现。本章负责把“程序是怎么变成进程的”讲清楚，第8章负责把“调试信息是怎么描述程序的”讲清楚，第9章再把它们接起来。

本章讲什么

本章按“从源码到进程”的顺序展开：

  • 7.1–7.5：程序是怎么构建、链接、加载的。 跟着一次 go build，看编译器、汇编器、链接器各自留下什么；再认识 ELF 的文件头、节头表、段头表；然后看符号表、符号解析、重定位，最后看加载器如何把 PT_LOAD 映射进进程地址空间。
  • 7.6：文件地址、链接地址与运行时地址。 这是调试器地址转换的核心：符号表和 DWARF 里是链接地址，进程里是运行时地址，两者差一个装载偏置。这一节补上很多调试器教程会跳过、但一写就撞墙的一环。
  • 7.7：用 Go 标准库读取 ELF 与符号表。 debug/elf 和 debug/gosym 能帮我们省掉大量解析工作；debug/dwarf 不在本章展开，因为它需要先理解第8章的 DWARF 数据模型。
  • 7.8：从二进制到 DWARF。 收束本章，交代调试信息在构建流程中的位置，并进入第8章。

为什么要讲这些，能不能跳

如果你只想尽快写出一个能用的符号级调试器，本章确实有一部分内容可以晚点读。但完全不读，后面会遇到几类让你抓狂的问题，反而会因此陷入窘境：

  1. 断点地址算错。 PIE 程序里，DWARF 的 low_pc 和符号表里的地址都是链接地址；不换算装载偏置，int3 会写到未映射的页上，或者写错位置，断点永远不命中。第9章的 StaticBase、断点地址转换、core 文件调试都依赖 7.6。
  2. 符号来源搞混。 .symtab、.dynsym、.gopclntab、DWARF 的 .debug_info 都能提供“名字 → 地址”的能力，但适用场景不同：strip 后还剩什么、cgo 和 plugin 的符号在哪里、为什么 delve 有时候还要读 TLS 符号。这些问题的答案在 7.3 和 7.7。
  3. 调试信息为什么读不到。 .debug_* 不会被加载到进程内存，压缩、分离调试信息、build ID 都会影响调试器从哪里读、读到的是不是链接地址。这些在 7.2、7.5 和第8章都会反复出现。

所以，本章不是一本微缩版链接器教材，而是调试器的“地址模型 + 二进制地图”。你可以按下面的路线读，不必平均用力。

  • 7.4 符号解析与重定位 是本章最深入链接器、也最枯燥乏味的一节。第一遍读不懂没关系，先把“链接时地址 ≠ 运行时地址”“动态链接器在加载时还要做一次重定位”这两句话记住；等第9章遇到 PIE、cgo、plugin 再回来查。

关于“符号”这个术语

“符号”在不同阶段扮演着不同的角色，携带的信息也各有侧重，后面我们会反复遇到，这里先统一一下：

  • .symtab 中的符号信息：链接器在链接时使用各目标文件（.o）中的 .symtab 进行符号解析和重定位，据此将不同的代码段和数据段组合成可执行文件；链接器在最终产物中合并生成的 .symtab 通常包含函数地址、全局变量地址等，主要供 nm、readelf 等工具使用（被 strip 移除也不影响程序运行）。加载时若涉及动态链接，则由动态链接器基于 .dynsym（动态符号表）完成符号解析，与 .symtab 无关。
  • .debug_info（或 .debug_*）中的信息：主要面向调试器，用于提供源码级别的调试信息，例如类型名、变量名、函数名等。这些信息以 DWARF 的 DIE（Debugging Information Entry）形式存储。调试器利用这些信息进行符号显示、断点设置、单步调试等操作。
  • 编译器在词法分析、语法分析和语义分析阶段：会对源码中的类型名、变量名、函数名等符号进行分析，并生成包含更详细信息的内部符号表（不是 .symtab）。这些信息不仅用于类型安全检查等分析过程，也为后续的优化和代码生成提供依据。

注意不同情景下提到“符号”这个术语，读者不要混淆相关的含义和技术细节。

本章与第8章的分工

第7章结束时，你应该能回答：

  • 一个 Go 程序从源码到进程，经历了哪些阶段，每个阶段留下了什么；
  • 调试信息存放在 ELF 的哪些 section，为什么它们不会被加载到进程内存；
  • 符号表、.gopclntab、DWARF 各自能提供什么，strip 之后还剩什么；
  • 为什么调试器需要装载偏置，怎么从 AT_ENTRY、/proc/<pid>/maps、link_map 里拿到它。

第8章结束时，你应该能回答：

  • DWARF 用 DIE、Tag、Attribute 怎么描述类型、变量、函数；
  • 行号表怎么把 file:line 变成 PC，CFI 怎么把 PC 展开成调用栈；
  • Go 工具链怎么生成这些数据，标准库 debug/dwarf 能读什么、不能读什么；
  • godbgv2 为什么自研 pkg/dwarf、在哪些地方参考 delve，以及怎么读出一个变量。

如果你对 ELF、链接、加载已经很熟，可以直接按快速通道进入第8章；如果读到这里还有些概念不踏实，也别急，第8章会反复用到它们。我们开始吧。
